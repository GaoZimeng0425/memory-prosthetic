# Memory Prosthetic - Epic Breakdown: 用户自建笔记功能

## Overview

本文档提供 Memory Prosthetic "用户自建笔记功能" 的完整史诗和故事分解，将需求从架构文档、UX 设计规范和项目上下文分解为可实施的故事。

## Requirements Inventory

### Functional Requirements

**FR1**: 用户可以在桌面应用中创建新的笔记，无需依赖网页收集功能

**FR2**: 笔记支持富文本编辑，使用 Plate.js 编辑器，用户可以输入和格式化文本内容（支持标题、粗体、斜体、列表、代码块、表格等）

**FR3**: 笔记必须包含标题字段，标题为必填项

**FR4**: 笔记内容字段支持富文本格式（Plate.js Slate 格式），支持多行文本输入和格式化

**FR5**: 用户可以为笔记设置收藏夹（favorite），与现有收藏夹系统集成

**FR6**: 用户可以为笔记添加标签（tags），与现有标签系统集成

**FR7**: 用户创建的笔记可以参与语义搜索，使用现有的 Embedding 和向量搜索能力

**FR8**: 用户创建的笔记在搜索结果中显示，与收集的内容统一展示

**FR9**: 用户可以在笔记详情页编辑笔记标题和内容

**FR10**: 用户可以在笔记详情页删除笔记

**FR11**: 用户创建的笔记支持归档和恢复功能，与现有状态管理系统一致

**FR12**: 笔记列表页面可以筛选和显示用户创建的笔记

**FR13**: 笔记创建时自动生成 Embedding 向量，用于语义搜索

**FR14**: 笔记支持与收集的内容使用相同的组织方式（收藏夹、标签、状态）

**FR15**: 笔记创建界面提供 Plate.js 富文本编辑器，使用 `@memory-prosthetic/editor` 包中的编辑器组件

**FR16**: 笔记可以设置创建时间和更新时间，自动记录时间戳

**FR17**: 笔记内容以 Plate.js Slate JSON 格式存储，支持完整的富文本格式保留

**FR18**: 笔记在搜索结果和列表视图中可以正确显示，需要将 Slate 格式转换为 Markdown 用于渲染

**FR19**: 笔记的 Embedding 生成需要将 Slate 格式转换为纯文本，确保语义搜索的准确性

**FR20**: 所有内容（包括收集的文章和用户创建的笔记）都需要有分类（type）字段，用于区分内容类型

**FR21**: 系统支持以下分类类型：`网页`、`代码`、`音频`、`视频`、`笔记`、`文件`

**FR22**: 从浏览器插件收集的内容自动分类为 `网页`

**FR23**: 用户创建的笔记自动分类为 `笔记`

**FR24**: 用户可以在创建或编辑内容时手动选择或修改分类

**FR25**: 内容列表和搜索结果可以按分类筛选和显示

**FR26**: 分类信息在内容卡片和详情页中显示，帮助用户快速识别内容类型

**FR27**: 现有所有已保存的内容（collections）默认分类为 `网页`，需要数据迁移

### NonFunctional Requirements

**NFR1**: 笔记创建操作响应时间应 < 500ms（不含 Embedding 生成时间）

**NFR2**: 笔记编辑保存操作响应时间应 < 300ms

**NFR3**: 笔记内容支持最大长度限制（建议 10MB 或 100 万字符），防止性能问题。Plate.js Slate JSON 格式需要考虑序列化后的存储大小

**NFR4**: 笔记的 Embedding 生成应在后台异步进行，不阻塞用户操作。需要将 Plate.js Slate 格式转换为纯文本用于 Embedding 生成

**NFR5**: 笔记数据存储在本地 SQLite 数据库，复用 `collections` 表，`url` 字段为 NULL 表示用户创建的笔记

**NFR6**: 笔记功能应遵循现有的数据模型和 API 设计模式

**NFR7**: 笔记编辑界面应遵循现有的 UX 设计规范，保持体验一致性

**NFR8**: 笔记功能应支持离线使用，无需网络连接

**NFR9**: 笔记创建和编辑应提供适当的错误处理和用户反馈

**NFR10**: 笔记功能应与现有的搜索、组织、筛选功能无缝集成

**NFR11**: 分类功能应支持快速筛选，筛选操作响应时间 < 200ms

**NFR12**: 分类数据应存储在数据库中，支持索引优化查询性能

### Additional Requirements

**技术架构要求：**

- **数据库 Schema 扩展**:
  - **决策**: 复用 `collections` 表，将 `url` 字段改为可选（NULL 值表示用户创建的笔记）
  - **迁移需求**:
    - 需要数据库迁移脚本，将 `url` 字段从 `NOT NULL` 改为可选的 `TEXT`
    - 需要添加 `type` 字段（TEXT NOT NULL DEFAULT '网页'），用于存储内容分类
    - 现有所有记录的 `type` 字段需要设置为 `'网页'`
  - **类型区分**:
    - 通过 `url IS NULL` 判断是否为用户创建的笔记
    - 通过 `type` 字段区分内容分类（`网页`、`代码`、`音频`、`视频`、`笔记`、`文件`）
- **类型定义**:
  - 需要在 `packages/shared/src/types/collection.ts` 中扩展 `Collection` 类型：
    - 使 `url` 字段可选（`url?: string`）
    - 添加 `type` 字段（`type: CollectionType`）
  - 需要定义 `CollectionType` 类型：`'网页' | '代码' | '音频' | '视频' | '笔记' | '文件'`
- **Rust 数据层**:
  - 需要在 `apps/desktop/src-tauri/src/db/collections.rs` 中扩展 CRUD 操作：
    - 支持 `url` 为 NULL 的情况
    - 支持 `type` 字段的读取和写入
    - 支持按 `type` 筛选查询
- **Tauri Commands**: 需要在 `apps/desktop/src-tauri/src/commands/` 中实现笔记相关的命令（create_note, update_note, delete_note），复用现有的 collection 命令或扩展
- **HTTP API 端点**: 需要在 `apps/desktop/src-tauri/src/server/` 中添加笔记相关的 API 端点（可选，如果通过 Tauri IPC 实现则不需要）
- **前端组件**:
  - 需要在 `apps/desktop/src/components/features/` 中创建笔记编辑器组件
  - **编辑器实现**: 使用 `@memory-prosthetic/editor` 包中的 `PlateEditor` 组件
  - 需要处理 Plate.js Slate 格式与 Markdown 的转换（用于存储和 Embedding）
  - 需要创建分类选择器组件，支持在创建/编辑内容时选择分类
  - 需要在内容列表和搜索结果中添加分类筛选器
- **前端路由**: 需要在 `apps/desktop/src/routes/` 中添加笔记创建和编辑页面
- **Embedding 集成**: 笔记创建后需要自动触发 Embedding 生成，使用现有的 `embedding/` 模块。需要将 Plate.js Slate 格式转换为纯文本或 Markdown 用于 Embedding

**UX 设计要求：**

- **创建入口**: 需要在主界面或搜索界面提供"新建笔记"按钮或快捷键
- **编辑器体验**:
  - 使用 Plate.js 富文本编辑器，提供完整的格式化工具栏
  - 遵循现有的 UX 设计规范，支持键盘快捷键（如 Cmd+S 保存、Cmd+B 粗体等）
  - 编辑器应支持 Plate.js 的所有核心功能（标题、列表、代码块、表格、链接等）
- **内容存储**: 笔记内容以 Plate.js Slate 格式（JSON）存储，需要实现与 Markdown 的双向转换用于：
  - 显示：在搜索结果和列表中使用 Markdown 渲染（streamdown）
  - Embedding：转换为纯文本用于语义搜索
- **响应式设计**: 笔记编辑界面应适配不同窗口大小，遵循现有的响应式设计模式

**集成要求：**

- **搜索集成**:
  - 笔记应参与现有的语义搜索，搜索结果中应能区分笔记和收集的内容（可选：通过图标或标签标识）
  - 搜索结果应支持按分类筛选
- **组织集成**:
  - 笔记应支持现有的收藏夹和标签系统，可以在侧边栏中按收藏夹/标签筛选笔记
  - 侧边栏应支持按分类筛选内容
- **状态管理**: 笔记应支持现有的状态系统（active, archived, deleted），与收集的内容使用相同的状态管理逻辑
- **分类集成**:
  - 分类筛选应与现有的收藏夹、标签、状态筛选组合使用
  - 分类信息应在内容卡片、列表、详情页中显示

**数据模型决策：**

- **URL 字段处理**:
  - **已决策**: 将 `collections.url` 字段改为可选（NULL）
  - **实现方式**: 用户创建的笔记 `url` 为 NULL，收集的内容 `url` 为实际 URL
  - **数据库迁移**: 需要创建迁移脚本，将 `url TEXT NOT NULL` 改为 `url TEXT`
  - **向后兼容**: 现有收集的内容不受影响，`url` 字段保持有值
- **类型区分**:
  - 通过 `url IS NULL` 判断是否为用户创建的笔记
  - 通过 `type` 字段区分内容分类
- **内容格式**:
  - **存储格式**: 笔记内容以 Plate.js Slate JSON 格式存储（或序列化为 JSON 字符串）
  - **转换需求**: 需要实现 Slate → Markdown 和 Markdown → Slate 的转换工具
  - **Embedding 输入**: 将 Slate 格式转换为纯文本用于 Embedding 生成
- **分类系统**:
  - **分类类型**: `'网页' | '代码' | '音频' | '视频' | '笔记' | '文件'`
  - **默认分类**: 收集的内容默认为 `'网页'`，用户创建的笔记默认为 `'笔记'`
  - **分类选择**: 用户可以在创建/编辑时选择或修改分类
  - **数据迁移**: 现有所有记录的 `type` 字段需要设置为 `'网页'`

## Architecture Decision Records (ADR)

本文档记录了"用户自建笔记功能"的关键架构决策，包括决策背景、方案对比、权衡分析和最终决策理由。

### ADR-001: 数据模型设计 - 复用 collections 表 vs 新建 notes 表

**状态**: ✅ 已决策
**决策日期**: 2025-01-27
**决策者**: 架构团队

#### 决策点

如何存储用户创建的笔记？

#### 方案对比

**方案 A: 复用 collections 表（url 可选）** ✅ 已选择

**优势：**

- 统一数据模型，减少代码重复
- 复用现有 CRUD、搜索、组织功能
- 查询简单，无需 JOIN
- 迁移成本低（仅需修改 url 字段）

**劣势：**

- url 字段语义不清晰（NULL 表示笔记）
- 未来扩展可能受限

**方案 B: 新建独立的 notes 表**

**优势：**

- 语义清晰，职责分离
- 可独立扩展（如添加 notes 特有字段）
- 类型安全（TypeScript 可区分）

**劣势：**

- 代码重复（需要新的 CRUD 操作）
- 查询复杂（需要 UNION 或分别查询）
- 维护成本高（两套逻辑）
- 搜索和组织功能需要统一处理

**方案 C: 使用继承/组合模式**

**优势：**

- 兼顾语义清晰和代码复用

**劣势：**

- 实现复杂（Rust 中需要 trait 或枚举）
- 查询性能可能受影响
- 过度设计，不符合当前需求

#### 权衡分析

| 维度 | 方案 A（复用表） | 方案 B（独立表） | 方案 C（继承模式） |
|------|-----------------|-----------------|-------------------|
| 开发速度 | ⭐⭐⭐⭐⭐ | ⭐⭐ | ⭐ |
| 代码维护 | ⭐⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐ |
| 查询性能 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐ |
| 语义清晰 | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| 扩展性 | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ |

#### 决策

选择方案 A：复用 collections 表，url 字段可选。

#### 理由

1. **开发效率**: 复用现有功能，快速交付
2. **性能**: 单表查询，无需 JOIN
3. **维护成本**: 统一逻辑，降低维护负担
4. **风险**: 迁移简单，回滚容易
5. **未来扩展**: 通过 type 字段和 url IS NULL 可区分，必要时可重构

#### 缓解措施

- 通过 `url IS NULL` 明确区分笔记
- 使用 `type` 字段提供额外分类维度
- 文档化设计决策，便于未来重构

### ADR-002: 内容存储格式 - Slate JSON vs Markdown

**状态**: ✅ 已决策
**决策日期**: 2025-01-27
**决策者**: 架构团队

#### 决策点

笔记内容以什么格式存储？

#### 方案对比

**方案 A: 存储 Slate JSON** ✅ 已选择

**优势：**

- 保留完整格式信息（粗体、斜体、表格、代码块等）
- 与 Plate.js 编辑器原生兼容
- 支持复杂结构（嵌套列表、表格等）

**劣势：**

- 存储空间较大（JSON 结构）
- 需要转换工具用于展示和搜索
- 不易直接阅读（二进制/JSON）

**方案 B: 存储 Markdown**

**优势：**

- 人类可读，易于调试
- 存储空间小
- 无需转换即可展示
- 易于导出和迁移

**劣势：**

- 需要 Markdown → Slate 转换（编辑时）
- 转换可能丢失信息（复杂格式）
- 双向转换复杂且易出错

**方案 C: 双格式存储（Slate + Markdown）**

**优势：**

- 编辑用 Slate，展示用 Markdown
- 无需实时转换

**劣势：**

- 存储空间翻倍
- 数据一致性风险
- 同步成本高

#### 权衡分析

| 维度 | 方案 A（Slate JSON） | 方案 B（Markdown） | 方案 C（双格式） |
|------|---------------------|-------------------|-----------------|
| 格式完整性 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| 存储空间 | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐ |
| 编辑性能 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| 展示性能 | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| 维护复杂度 | ⭐⭐⭐ | ⭐⭐ | ⭐ |

#### 决策

选择方案 A：存储 Slate JSON 格式。

#### 理由

1. **格式完整性**: 保留 Plate.js 编辑器的所有格式
2. **编辑体验**: 无需转换，直接加载到编辑器
3. **未来扩展**: 支持更复杂的富文本功能
4. **转换成本**: 一次转换（展示时），可接受
5. **存储空间**: 现代数据库可处理 JSON 文本

#### 缓解措施

- 实现高效的 Slate → Markdown 转换工具
- 实现 Slate → 纯文本转换用于 Embedding
- 考虑压缩存储（如果 JSON 过大）
- 文档化转换规则和边界情况

### ADR-003: 格式转换策略 - 转换时机和方式

**状态**: ✅ 已决策
**决策日期**: 2025-01-27
**决策者**: 架构团队

#### 决策点

何时进行格式转换？如何实现？

#### 方案对比

**方案 A: 按需转换（存储时保持 Slate，使用时转换）** ✅ 已选择

**优势：**

- 存储格式统一（Slate）
- 转换逻辑集中管理
- 易于维护和测试

**劣势：**

- 每次展示都需要转换（性能开销）
- 转换逻辑可能成为瓶颈

**方案 B: 预转换缓存（存储 Slate，缓存 Markdown）**

**优势：**

- 展示时无需转换（从缓存读取）
- 性能最优

**劣势：**

- 需要缓存管理
- 数据一致性风险
- 存储空间增加

**方案 C: 存储时转换（存储 Markdown，编辑时转换）**

**优势：**

- 展示无需转换
- 存储格式人类可读

**劣势：**

- 编辑时需要 Markdown → Slate 转换
- 可能丢失格式信息
- 转换复杂

#### 权衡分析

| 维度 | 方案 A（按需转换） | 方案 B（预转换缓存） | 方案 C（存储时转换） |
|------|------------------|-------------------|-------------------|
| 实现复杂度 | ⭐⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐ |
| 性能 | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| 数据一致性 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐ |
| 维护成本 | ⭐⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐ |

#### 决策

选择方案 A：按需转换，存储时保持 Slate 格式。

#### 理由

1. **实现简单**: 单一数据源，无缓存同步问题
2. **数据一致性**: 避免缓存不一致
3. **性能可接受**: 转换操作轻量，可优化
4. **易于维护**: 转换逻辑集中，便于测试和调试

#### 优化措施

- 转换工具函数化，便于复用和测试
- 考虑使用 Web Worker 进行异步转换（如果转换耗时）
- 对频繁访问的内容考虑添加内存缓存（短期）
- 性能测试确保转换时间 < 50ms

### ADR-004: 分类系统设计 - type 字段 vs 独立分类表

**状态**: ✅ 已决策
**决策日期**: 2025-01-27
**决策者**: 架构团队

#### 决策点

如何实现内容分类系统？

#### 方案对比

**方案 A: 使用 type 字段（枚举类型）** ✅ 已选择

**优势：**

- 实现简单，查询快速
- 无需额外 JOIN
- 性能最优

**劣势：**

- 分类固定，扩展需修改代码
- 无法支持用户自定义分类

**方案 B: 独立分类表（categories）**

**优势：**

- 支持用户自定义分类
- 易于扩展
- 可添加分类元数据（图标、颜色等）

**劣势：**

- 需要 JOIN 查询
- 实现复杂度高
- 当前需求不需要自定义分类

**方案 C: 枚举类型 + 未来扩展**

**优势：**

- 当前使用枚举（性能好）
- 预留扩展接口（未来可支持自定义）

**劣势：**

- 需要设计扩展接口
- 可能过度设计

#### 权衡分析

| 维度 | 方案 A（type 字段） | 方案 B（分类表） | 方案 C（枚举+扩展） |
|------|-------------------|----------------|-------------------|
| 实现速度 | ⭐⭐⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐ |
| 查询性能 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| 扩展性 | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| 复杂度 | ⭐⭐⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐ |

#### 决策

选择方案 A：使用 type 字段（枚举类型）。

#### 理由

1. **满足当前需求**: 6 种固定分类已足够
2. **性能最优**: 无需 JOIN，查询快速
3. **实现简单**: 快速交付
4. **未来扩展**: 如需自定义分类，可迁移到分类表

#### 缓解措施

- 使用 TypeScript 枚举确保类型安全
- 文档化分类系统设计，便于未来扩展
- 预留扩展接口（如分类元数据字段）

#### 关键原则

1. **优先开发速度和维护性**: 选择简单、可维护的方案
2. **性能可接受**: 在满足需求的前提下优化性能
3. **保持简单**: 避免过度设计，YAGNI 原则
4. **为未来扩展预留接口**: 文档化设计，便于未来重构

**Given** 用户在笔记创建或编辑界面
**When** 查看标签选择器
**Then** 显示现有的标签列表（与收集的内容使用相同的标签系统）
**And** 显示标签输入框，支持多个标签选择
**And** 显示已有标签建议（自动补全）
**And** 用户可以选择或创建新标签
**And** 保存后笔记与选中的标签建立关联（`collection_tags` 表）
**And** 笔记可以在侧边栏中按标签筛选显示

## Epic 4: 搜索和展示集成

用户创建的笔记可以参与语义搜索，在搜索结果中与收集的内容统一展示，可以在列表中筛选和显示笔记。

### Story 4.1: 笔记语义搜索集成

As a 用户,
I want 通过语义搜索找到我创建的笔记,
So that 可以使用模糊记忆检索笔记内容。

**Acceptance Criteria:**

**Given** 用户已创建笔记并生成了 Embedding 向量
**When** 用户在搜索框输入查询
**Then** 笔记参与语义搜索（使用现有的向量搜索功能）
**And** 搜索结果包含匹配的笔记
**And** 搜索结果按相关性排序
**And** 笔记在搜索结果中正确显示（标题、内容预览）

### Story 4.2: 搜索结果统一展示

As a 用户,
I want 在搜索结果中同时看到收集的内容和笔记,
So that 可以统一查看所有相关内容。

**Acceptance Criteria:**

**Given** 用户执行搜索
**When** 查看搜索结果
**Then** 搜索结果同时包含收集的内容和用户创建的笔记
**And** 笔记和收集的内容在同一个结果列表中显示
**And** 可以通过图标或标签区分笔记和收集的内容（可选）
**And** 搜索结果格式统一（标题、预览、时间等）

### Story 4.3: 笔记列表筛选和显示

As a 用户,
I want 在内容列表中筛选和显示笔记,
So that 可以查看所有我创建的笔记。

**Acceptance Criteria:**

**Given** 用户在内容列表页面
**When** 查看筛选选项
**Then** 提供筛选选项（如"仅显示笔记"）
**And** 选择筛选后，列表只显示用户创建的笔记（`url IS NULL`）
**And** 笔记在列表中正确显示（标题、内容预览、时间等）
**And** 筛选操作响应时间 < 200ms

### Story 4.4: 笔记详情页展示

As a 用户,
I want 在笔记详情页查看完整的笔记内容,
So that 可以阅读和编辑笔记。

**Acceptance Criteria:**

**Given** 用户点击搜索结果或列表中的笔记
**When** 打开笔记详情页
**Then** 显示笔记标题
**And** 将 Slate 格式转换为 Markdown 并正确渲染（使用 streamdown）
**And** 显示笔记的创建时间和更新时间
**And** 显示笔记的分类信息（`type` 字段）
**And** 显示笔记的收藏夹和标签信息
**And** 提供编辑、删除、归档等操作按钮

## Epic 5: 分类筛选和展示增强

用户可以在创建或编辑内容时选择分类，可以在内容列表和搜索结果中按分类筛选，分类信息在内容卡片和详情页中清晰显示。

### Story 5.1: 分类选择器组件

As a 用户,
I want 在创建或编辑内容时选择分类,
So that 可以为内容设置正确的分类。

**Acceptance Criteria:**

**Given** 用户在内容创建或编辑界面
**When** 查看分类选择器
**Then** 显示分类下拉菜单或选择器组件
**And** 显示所有可用的分类选项：`网页`、`代码`、`音频`、`视频`、`笔记`、`文件`
**And** 用户可以选择一个分类
**And** 创建笔记时默认选择 `笔记` 分类
**And** 收集内容时默认选择 `网页` 分类
**And** 用户可以在编辑时修改分类

### Story 5.2: 分类筛选功能

As a 用户,
I want 在内容列表和搜索结果中按分类筛选,
So that 可以快速找到特定类型的内容。

**Acceptance Criteria:**

**Given** 用户在内容列表或搜索结果页面
**When** 查看筛选选项
**Then** 显示分类筛选器（支持多选）
**And** 用户可以选择一个或多个分类进行筛选
**And** 筛选后列表只显示选中分类的内容
**And** 分类筛选可以与收藏夹、标签、状态筛选组合使用
**And** 筛选操作响应时间 < 200ms

### Story 5.3: 分类信息展示

As a 用户,
I want 在内容卡片、列表和详情页中看到分类信息,
So that 可以快速识别内容的类型。

**Acceptance Criteria:**

**Given** 用户在内容列表、搜索结果或详情页
**When** 查看内容
**Then** 内容卡片显示分类标签或图标
**And** 分类信息清晰可见（使用颜色、图标或文字标识）
**And** 分类信息在详情页中显示
**And** 分类展示遵循现有的 UI 设计规范
